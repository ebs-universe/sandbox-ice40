# Derived Clocks and Prescalers

## Scope

This document describes the use of **derived clocks** in systems built around this clocking library, with particular focus on the `prescaler` module.

It explains:

* What derived clocks are
* Why they are discouraged by default
* When they are justified
* How to use them safely

This is an **advanced-use** section.

---

## What Is a Derived Clock?

A derived clock is a clock signal generated by dividing or manipulating another clock **inside the FPGA fabric**, rather than by using dedicated clocking primitives.

Examples include:

* Clock division using a counter bit
* Gated clocks
* Logic-generated clock enables used as clocks

The `prescaler` module generates such a clock.

---

## Architectural Position

The clocking library is intentionally designed so that **most timing problems do not require derived clocks**.

Instead, it promotes:

* Event-based timing
* Single-clock-domain logic
* Explicit CDC

Derived clocks exist as an **escape hatch**, not a default tool.

---

## The `prescaler` Module

### Role

`prescaler` divides an input clock using a synchronous binary counter and exposes the most significant bit as an output clock.

This produces:

* A free-running clock
* Approximately 50% duty cycle
* A new clock domain

---

### Key Properties

* `clk_out` is **not** routed through a global clock buffer
* Clock skew and insertion delay are uncontrolled
* Timing analysis becomes more complex
* CDC rules apply in both directions

These are inherent properties of fabric-generated clocks.

---

## When a Prescaler May Be Appropriate

Using a derived clock may be justified when:

### 1. External Clock Requirement

An external device requires:

* A clock pin
* A specific frequency
* Continuous clocking

Event pulses are insufficient in this case.

---

### 2. Extremely Slow Always-On Logic

For logic that:

* Runs very slowly
* Must remain active continuously
* Has minimal interaction with the rest of the system

A derived clock can reduce toggling and power.

---

### 3. Legacy or Fixed-Interface Blocks

Some blocks:

* Expect a clock
* Cannot be easily refactored to event-driven logic

In these cases, isolating the block in its own domain may be cleaner.

---

## When a Prescaler Should *Not* Be Used

Derived clocks should not be used:

* As a convenience replacement for `periodic_tick`
* For FSM stepping
* For intra-domain timing
* To “simplify” logic

If the logic can be expressed using events, it should be.

---

## Example: Slow External Interface Clock

### Scenario

An external peripheral requires a 100 kHz clock.

### Implementation

```verilog
prescaler #(
    .N(9)  // 48 MHz / 2^9 ≈ 93.75 kHz
) u_prescaler (
    .clk_in  (clk_sys),
    .clk_out (clk_ext)
);
```

### Notes

* Frequency is approximate
* Clock quality depends on `clk_sys`
* CDC is required for any interaction with `clk_sys` logic

---

## CDC Considerations with Derived Clocks

When using `prescaler`:

* `clk_out` defines a new domain
* Reset must be synchronized to `clk_out`
* Data crossing between domains must use CDC patterns

Derived clocks do not reduce CDC complexity — they increase it.

---

## Registration Heuristics

Logic in a derived-clock domain should:

* Be self-contained
* Minimize interaction with other domains
* Use registered interfaces at boundaries

If frequent interaction is required, a derived clock is likely the wrong abstraction.

---

## Power and Timing Tradeoffs

Derived clocks may:

* Reduce toggle rate
* Reduce dynamic power locally

But they also:

* Complicate timing closure
* Increase verification burden
* Reduce portability

These tradeoffs must be explicit and justified.

---

## Relationship to `timebase` and `periodic_tick`

* Derived clocks bypass the time/event model
* They operate outside the library’s main guarantees
* They should not interact directly with timing signals

If both are used:

* Treat them as separate subsystems
* Keep boundaries narrow and well-defined

---

## Summary

Derived clocks are:

* Powerful
* Dangerous
* Occasionally necessary

The clocking library:

* Supports them explicitly
* Warns against casual use
* Provides guidance for safe integration

If a design requires many derived clocks, the architecture should be reconsidered.
